# 团队编排

## 角色模型

- 主 Agent 是需求、方向与集成负责人：吃透用户需求，对设计品位、架构方向和“是否值得这样做”拍板，维护依赖图、任务 owner、权限和最终验收。
- 任务 owner 是能力相当的同事：对分配边界内“怎么做”全权负责，包括调查、实现方案、实现、测试、提交和交付。
- 不让主 Agent 预先完成大部分调查再把编码余量交给 owner。若主 Agent 预计或实际承担约千行以上的主要实现，重新检查任务是否应该拆分或转交；该数字是警戒线，不是机械门禁。
- 每个交付边界只设一个 owner。共享契约、集成和生产执行也要有明确 owner。
- 单独的文档或规则更新（任务本身就是新增或改写规则条目、修正文档表述、把用户口述的经验写进文档）由主 Agent 亲自完成，不派给 owner；主 Agent 掌握用户原话和讨论上下文，更能写准核心要点。owner 在执行任务过程中仍可写、改所有与该任务相关的文档，例如事件记录、进度和受影响的规则与说明。

## 派发前

派发前完成只有主 Agent 能做的部分，不做 owner 自己能做的调查：

- 澄清需求：理解用户要什么、为什么要、做到什么程度算完；补全用户没说但显然在意的部分；存在会影响结果的歧义时先问用户，必要时一起讨论方案。
- 拍板方向：涉及设计品位或架构取舍的任务，先形成决定，用意图、效果和底线表达。例如演示文稿写清受众、叙事主线、视觉调性、信息密度和不可接受的效果，不写用什么工具、每页放什么。
- 项目整体判断：确认任务与已有功能、项目约定的关系，以及是否存在可能让任务不必自己实现的现成方案。主 Agent 只判断方向，具体检索交给 owner；owner 发现现成方案时直接采用并在交付中说明。
- 派发前的准备以分钟计，不为写任务包做大量调查；需求明确就立即派发。
- 主 Agent 已掌握全部事实、剩下的只是几条命令时，自己直接做，不派发。只有需要较长的调查或实现、多系统联动、长时间运行，或 owner 已持有关键上下文、主 Agent 现学成本更高时才派发。主 Agent 不会某个操作时，先向 owner 要方法或看它留下的证据，再自己执行。

## 建立任务拓扑

先识别依赖和冲突面，再决定 Agent 数量：

- 共享 Schema、领域类型、公共接口、路由、组件 API、迁移、测试基座或同一运行现场，默认视为潜在依赖。
- 全局重构若改变共享契约，先由一个 owner 收口契约，再派生功能和 UI 任务；严格局部且不影响其他边界时才并行。
- 多个功能动作边界独立时可分别委派；多个 UI 需求落在同一页面或组件系统时，优先由一个 UI owner 统一处理。
- 主 Agent 占用一个协作槽位。只在存在空闲槽位且任务边界独立时创建新 Agent。

新需求到达时：

- 与进行中任务独立且有空槽：创建新 owner。
- 与现有 owner 的文件、契约或现场重叠：交给该 owner 后续完成，或等待其交付后再派发。
- 无空槽：进入有序队列，优先复用最早完成且领域相近的 Agent。
- 紧急需求与现有任务冲突：暂停、缩小或重排原任务，明确新的 owner 后再继续；不得让两个 Agent 竞争同一语义面。

## 委派任务包

任务包是写给同事的简报，只写 owner 自己拿不到的东西：

```text
意图：用户要什么、为什么要；用户原话中的关键要求
决定：主 Agent 已拍板的方向（只写真正拍板的少数几条，没有就省略）
完成标准：验收时看什么；默认包含按用户授权完成提交、部署和真实环境验证
授权：用户已授予的范围原样转达（如外呼测试号码、生产部署）；禁止事项只写用户或项目明确禁止的
自主：遇到兼容问题、约定冲突、决定未覆盖的取舍、成本超预期或发现现成方案时，自行按用户意图决定并继续，写进交付摘要；只在「停下汇报」所列情况停止。不得经即时消息、桌面通知等渠道直接询问或通知用户
交付：附上本文「交付摘要」的结构和要求原文（owner 未必加载本 skill）
```

任务包以主 Agent 的口吻直接陈述任务，像同事之间布置工作；用户原话需要保留时作为“意图”中的引文出现。不要用“用户叫你做：”“用户追加了命令：”“以下是用户的要求”之类的转述外壳包裹任务，追加（`send`/`steer`）同样直接写要补充或调整的内容。

主 Agent 已核实的事实连同证据写进任务包，owner 直接采信，不重新调查。项目规则要求的写入前现场复核照常执行（如邀请前刷新席位），但只复核本次要写的对象，不扩大核查范围。

不写进任务包的内容：

- owner 能从仓库、文档、代码中自行获得的信息，如相关文件、可复用实现、项目约定、测试命令。
- 未经证据验证的根因、实现步骤、文件清单或测试清单。
- 主 Agent 自己担心但用户和项目都没禁止的“稳妥起见”限制；里程碑之间的汇报检查点。

多阶段任务（M1、M2……）整体派给同一 owner 连续完成，不逐阶段派发验收。主 Agent 想看中间进度时读提交、日志和 `status`，不要求 owner 停下。

owner 由主 Agent 自己启动、追加和监督，不让用户手动启动或转达。监督按[Codex 会话控制](codex-control.md#等待)的空闲看门狗执行，不用定时轮询代替。

长任务要求 owner 在约定的工作目录维护进度文件（已完成步骤、追加决定、命令与退出码），上下文压缩或断线后从该文件续做，不重读全部文档。

### 生产运维执行任务

对真实账号、席位、凭证等生产对象按既定计划批量执行时，执行面没有设计空间，owner 只做确定的事：

- 计划由主 Agent 定稿：对象、分配、执行人和替补都写成确定数据。派发前把悬而未决的事实查清，属于用户的决定先问用户，不把“可能是……”“待确认”留给 owner。
- 前提核对按对象状态分别写判据，例如在池账号看当前监控结论、未入池候选看可复用性，不写一条对所有对象都要求的条件。
- 停止条件写成可观察的判据，并逐条写出处理顺序：自愈（重试、刷新、轮换出口等，写明次数）→ 换替补 → 停下。不用“人工验证”“异常”这类需要 owner 解释的词。
- 同类流程第二次出现时，主 Agent 应把它沉淀为项目工具，任务包引用工具和数据文件，不让 owner 每次现写脚本、重摸接口；来不及沉淀时记入项目待办。

## 停下汇报

只在以下情况停下，其余一律自主决定后继续：

- 需要用户新授权：删除生产数据、不可逆迁移、轮换凭据、扩大权限、改变既定拓扑、触达第三方或产生费用的真实外部动作（任务包未给出授权时）。
- 存在无法从用户意图推导、且会改变用户可见结果的产品决策。
- 继续需要的能力确实不可得（给出已尝试路径与证据）。

有多个停下事项时，先把其余能做的全部做完，再一次性汇报。

owner 只向主 Agent 汇报，不直接询问用户；完成通知也只出现在交付摘要中。主 Agent 收到汇报后：能从用户意图推导的直接拍板并在原会话中继续；只有确需用户决定的才转问用户，同时把其余可预见的授权一并问清，避免再次往返。

## Worktree 与提交

需要并行开发时，每个 owner 使用独立分支和 worktree：

1. 记录源仓库、基准提交和主工作区状态。
2. 由任务 owner 创建并只写入自己的 worktree；按项目要求独立安装依赖。
3. 主工作区有未提交代码时，明确哪些源码属于任务基线。只带入已跟踪或未忽略且获准的源码；保持基线与任务提交可区分。
4. owner 在 worktree 内完成调查、实现、测试、diff 审查和提交。worktree 提交是并行开发产物，不等同于主分支最终提交。
5. 交付前按项目约定同步最新主分支，解决自己边界内的冲突，重新验证，并保持分支和 worktree 干净。
6. 多个 owner 并行时，主 Agent 根据依赖顺序审查并语义合并任务提交，再在主工作区执行统一验证；单一 owner 且用户已授权交付到完成时，由 owner 自行合并、部署和验证。

不要让 owner 直接改主工作区代码，也不要让多个 Agent 共用一个 worktree。不得为回收方便擅自 `reset`、`restore`、`clean` 或强删仍含未确认产物的 worktree/分支。

若项目要求用户确认后才能提交，区分两种提交：owner 的任务分支提交用于可审查交付；主分支最终提交仍等待用户确认。更具体的项目规则优先。

## 调查与运行数据

允许任务 owner 发挥完整调查能力：

- 在任务授权范围内直接对主工作区或生产现场做只读调查，不要求主 Agent 代为收集证据。
- 同一真实账号、Profile、数据库快照或可变现场同时只分配给一个 owner；可能改变现场的诊断动作先升级确认。
- 凭证、Cookie、Token、验证码、私有配置和敏感正文不得进入 Agent 对话、Git、普通日志或稳定输出。
- 默认不把 `.env`、数据库、账号目录、运行目录、日志或其他被忽略的真实数据复制进 worktree。若项目明确允许诊断快照，必须限定来源、范围、目的、保留期和销毁方式。
- 测试使用临时目录和合成数据。把现场事实转成最小可复现测试，但不要求在调查前由主 Agent 预制 fixture。

真实写入必须走项目定义的正式入口：Schema 或确定性数据演进使用版本化 migration；业务动作使用 Application Service、持久任务/Operation 或等价入口；配置使用受管配置；文件资产使用受控的锁、staging 和原子替换。不要直接编辑生产数据库或运行资产来“修好本机”。

owner 可以设计和实现这些写入入口，并在隔离环境验证。用户已授权部署或发布到完成时，由 owner 自己合并、部署并做生产验证，不交回主 Agent；跨多个 owner 的集成才由主 Agent 或指定集成 owner 执行。

## `.env` 与私有配置

owner 负责实现配置读取、校验、错误信息、非敏感示例和测试，但不把真实值写入 Git 或交付消息。交付摘要的“配置变化”一项列出：

- 新增或变更的变量名及用途。
- 必填/可选、格式约束和缺失时行为。
- 主工作区需要补充的 `.env` 项。
- 需要重启的进程和验证命令。

主 Agent 在语义合并后汇总配置差异，按用户或项目授权写入私有环境并执行真实验证。

## 验收、集成与返工

验收先对照意图，再核对工程事实：

- 意图：结果是否达成用户意图、符合主 Agent 的决定和完成标准。品位类产出必须看实物，如渲染截图、打开页面或演示文稿，不以描述代替。
- 工程事实：提交与基准、任务独有 diff、测试、未跟踪文件、配置差异以及与其他提交的语义兼容性。owner 完成不等于任务收口。

主 Agent 按“共享契约与迁移 → 后端实现 → 前端调用 → 集成测试”的依赖方向集成；实际顺序以项目依赖图为准。

验收不通过或合并后出现问题时先复现并归类：

- 与意图或决定有差距：交回原 owner，说明差距在哪里、期望的效果是什么，不代为规定改法；品位细节可直接给出具体要求。
- 缺陷明确属于原任务边界：交回原 owner，提供失败命令、证据和预期行为。
- 问题来自多个任务的接口、共享契约或集成环境：由主 Agent 或指定集成 owner 处理。
- 修正极小、确定且不改变设计：主 Agent 可以直接完成，但需在交付中注明。

## 异常情况

- Agent 阻塞：要求其给出已验证事实、尝试、剩余假设和最小所需输入；能换路径继续时不立即接管。
- Agent 偏离范围或改变了已拍板的方向：先消息纠偏；继续造成风险时中断并保存现场，再重新分配。
- Agent 意外退出：保留 worktree、分支、提交和日志，按 [交接与恢复](handoff-and-recovery.md) 接续。
- 用户取消任务：停止新增动作，保留可恢复产物并汇报，不擅自清理。
- 两个任务产生重叠修改：停止机械合并，由主 Agent 基于契约做语义合并；必要时指定一个 owner 重新实现交叉部分。

## 交付摘要

要求任务 owner 按以下结构汇报，每项一两行，没有内容写“无”，不复述任务、不贴过程日志：

```text
结论：
产物：分支 / worktree / commit，或文件路径
验证：
配置变化：
风险与潜在冲突：
可能改变方向的发现：
```
